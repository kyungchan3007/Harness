# 0013 — 역할 식별 확인 + 역할별 권한 강제 — SDD

요구사항: [prd.md](prd.md)

## 설계
- **읽은 문서:** 0012 prd·sdd(역할·권한 표, 위험), 0008 hooks 입력 확인 결과(`agent_type`은 "보조 에이전트나 `--agent` 사용 시" 들어온다는 문서 기술 — 미검증), `records.mjs` `decideEdit`, `trace.mjs` `toEntry`
- **접근:**
  1. **먼저 확인(프로브):** 복사본에 hook 입력을 그대로 저장하는 임시 hook과 임시 보조 에이전트를 두고, (a) 메인 대화가 보조 에이전트를 불러 파일을 읽게 할 때, (b) `claude --agent`로 메인 대화 자체를 역할로 실행할 때, (c) 역할 없는 메인 대화일 때의 입력값을 비교한다.
  2. **결과가 "들어온다"면:** `records.mjs`에 `ROLE_PATHS`(역할 → 허용 경로 규칙)를 두고 `decideEdit(projectDir, relPath, role)`이 역할이 있으면 역할 규칙을 **기록 경로 허용보다 먼저** 적용(구현자가 prd를 고치지 못하게). builder의 코드 수정은 기존 규칙(작업 브랜치·prd·sdd)도 함께 요구.
  3. **보조 에이전트 정의:** `.claude/agents/{designer,builder,verifier}.md` — 역할·해야 할 일·금지·쓸 수 있는 도구(검사자는 Edit 없음).
  4. **자동 기록:** `toEntry`가 입력의 `agent_type`을 `role`로 남긴다.
- **대안·트레이드오프:**
  - 역할을 프롬프트로만 주기: 경계를 넘어도 못 막음. → hook 강제.
  - 역할마다 별도 git 브랜치·폴더로 식별: `agent_type`이 없을 때의 대안. 실험 흐름이 복잡해진다. → 프로브 결과가 부정적일 때만.
  - 역할 규칙을 기록 경로 허용 뒤에 적용: 구현자가 prd·sdd를 고칠 수 있게 되어 "스펙을 코드에 맞춰 고치는" 문제를 못 막음. → 역할 규칙을 먼저.
  - 검사자 Bash 금지: 테스트를 못 돌려 판정 근거가 약해짐. → Bash 허용, 대신 Bash 쓰기는 사전 차단 못 하는 한계로 명시(0009와 동일).
- **파일 계획:** `.claude/agents/{designer,builder,verifier}.md`, `hooks/lib/records.mjs`(+test), `hooks/guard.mjs`, `hooks/trace.mjs`(+test), 지침서(guardrails.md)
- **위험:** 프로브에서 `agent_type`이 안 들어오면 2~4의 식별 방식을 바꿔야 한다 → 프로브를 구현보다 먼저.
- **검증 계획:** 프로브 3종(원본 입력 보관), 역할별 허용·차단 단위 테스트, 실제 보조 에이전트가 권한 밖 파일을 고치려 할 때 차단되는지 e2e, `pnpm check`

## 계획과 달라진 점
- 없음 — 프로브 결과가 긍정적이라 설계대로 구현. 다만 e2e ②(검사자 → 코드 수정)는 첫 시도에서 **hook까지 가지 않았다.** 검사자 정의에 Edit 도구가 없어 에이전트가 스스로 거절했기 때문. Write 도구로 다시 시도해 hook 차단을 확인했다(도구 제한 + hook = 이중 방어).

# 0022 — 원문 고정 강제 — SDD

요구사항: [prd.md](prd.md)

## 설계
- **읽은 문서:** 0016 sdd(B 실패 원인·B′ 결과), 0013 sdd(`agent_id`는 보조 에이전트 호출 시에만, `--agent` 모드엔 없음), `records.mjs` `decideEdit`·`inspectTask`, `verdict.mjs`, `trace.mjs` `toEntry`, `guard.mjs`
- **접근:**
  1. **원문 파일** `request.md` — `pnpm request <이슈>`(`evals/request.mjs`)가 `gh issue view`로 본문을 받아 `---` 앞까지(닫을 때 채우는 칸 제외)를 머리말과 함께 쓴다. 이미 있으면 덮어쓰지 않는다.
  2. **실행 번호 기록** — `toEntry`가 `agent_id`를 `agent`로 남긴다(없으면 기록 안 함). 같은 역할이라도 실행(호출)마다 번호가 달라 "이번 실행에서 읽었나"를 판단할 수 있다. `--agent` 모드처럼 번호가 없으면 세션 번호로 대신한다.
  3. **수정 판단 순서** (`decideEdit`):
     - ① 원문 고정 — 대상이 `specs/*/request.md`: 이미 있으면 모두 차단, 없으면 역할 없는 메인만 허용
     - ② 읽기 전 차단 — 역할 에이전트이고 현재 태스크 폴더에 `request.md`가 있는데, 자동 기록에 **같은 실행 번호의 `request.md` 읽기**가 없으면 차단("먼저 읽으세요")
     - ③ 기존 역할 권한(0013) → 기록 경로 → 기록 강제(0009)
  4. **판정서** — `parseVerdict`에 `requireSourceCheck` 옵션: 회차마다 `### 원문 대조`가 있고 비어 있지 않아야 한다. `inspectTask`는 `request.md`가 있으면 켠다.
  5. **완료 검사** — prd에 `역할 분리: on`인데 `request.md`가 없으면 실패.
  6. **지시·템플릿** — 세 역할 지시에 "시작하면 `request.md`부터 읽는다, 원문과 prd가 다르면 원문이 기준", 검사자 지시·판정서 템플릿에 `### 원문 대조`.
- **대안·트레이드오프:**
  - 프롬프트로만 지시(B′ 방식): 효과는 확인됐지만 지키는 건 조율자 몫. → 장치로.
  - 보조 에이전트 시작 시 원문을 자동 주입: 가장 확실하지만 시작 시점 hook으로 보조 에이전트 문맥에 넣는 방법을 확인하지 못함. → 읽기 강제로 같은 효과, 주입은 후속 검토.
  - 역할 단위로 "한 번 읽었으면 통과": 2차 구현자처럼 새로 불린 실행은 원문을 모르는데 통과됨. → 실행 번호 단위.
  - 원문 대조를 반려에만 요구: 0016의 실패는 **통과**에서 일어났다. → 통과·반려 모두.
- **파일 계획:** `hooks/lib/records.mjs`, `hooks/lib/verdict.mjs`, `hooks/trace.mjs`, `hooks/guard.mjs`, `evals/request.mjs`, `package.json`, `.claude/agents/*.md`, `templates/verdict.md`, `guardrails.md`, 테스트, `experiments/role-split/run.mjs`(새 그룹)
- **위험:**
  - 자동 기록 파일을 못 읽으면(경로·형식) 모든 역할 수정이 막힘 → 단위 테스트 + 실제 실행으로 확인.
  - 읽기 기록은 수정 직전 검사가 아니라 도구 사용 **후** 남는다 → 같은 실행에서 읽은 뒤 수정하면 이미 기록됨(순서 문제 없음).
  - 조율자가 `request.md`를 요약으로 새로 만들 수 있다(메인은 생성 허용) → 실험에서는 실행 스크립트가 원문을 미리 둠. 실제로는 `pnpm request` 사용을 지침으로.
- **검증 계획:** 판단 함수·판정서·원문 복사 단위 테스트, 실제 실행 — 0016 B 프롬프트 그대로 새 장치로 3회(그룹 `BR`), 0016 B(4·5·20)와 비교, `pnpm check`

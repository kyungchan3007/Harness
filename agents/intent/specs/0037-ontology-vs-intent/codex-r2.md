다만 다음 두 사항은 정리해야 합니다.

- 기존 업무 값 검사는 할인율·금액 등의 어휘에 치우쳐 있습니다. 시료 도메인의 업무 가정을 완전히 탐지한다고 해석하면 안 됩니다. 그대로 쓰거나 공통으로 수정하되, 파일럿 전에 결정하고 오탐·미탐을 기록하세요.

**4. 시료 도메인 — 수용, 다음 구체안 권장**

과제는 **“가상 연구실의 시료 분취·예약·소비·보관 이력 엔진”**으로 잡겠습니다. 실제 연구·의료 관행을 추측할 필요가 없도록 아래 정책을 공통 request에 모두 명시합니다.

공개 API는 인메모리·단일 프로세스·순차 호출로 제한합니다. 저장소·동시성·실제 시각은 제외합니다.

```ts
type ID = string;
type Qty = number; // 정수 μL
type Result<T> =
  | { ok: true; value: T }
  | { ok: false; code: ErrorCode };

interface Lab {
  receive(eventId: ID, input: {
    sampleId: ID; containerId: ID; custodianId: ID; qty: Qty;
  }): Result<Receipt>;

  split(eventId: ID, parentId: ID, children: Array<{
    sampleId: ID; containerId: ID; qty: Qty;
  }>): Result<Receipt>;

  reserve(eventId: ID, input: {
    reservationId: ID; sampleId: ID; qty: Qty;
  }): Result<Receipt>;

  cancel(eventId: ID, reservationId: ID): Result<Receipt>;
  consume(eventId: ID, reservationId: ID): Result<Receipt>;
  discard(eventId: ID, sampleId: ID): Result<Receipt>;

  move(eventId: ID, sampleId: ID,
       targetContainerId: ID): Result<Receipt>;

  transferCustody(eventId: ID, sampleId: ID,
                  custodianId: ID): Result<Receipt>;

  snapshot(): Snapshot;
}

declare function createLab(catalog: {
  locationIds: ID[];
  custodianIds: ID[];
  containers: Array<{
    containerId: ID; locationId: ID; capacity: Qty;
  }>;
}): Lab;
```

容器の位置は固定、`move` は試料を別容器へ移す操作とします。`Snapshot` には試料、予約、成功イベント履歴を含め、試料では親ID・根ID・残量・予約量・状態・容器ID・責任者IDを観測できるようにします。`Receipt` は成功イベントIDと連番です。

IDは種類ごとに一意で、異なる種類のIDには同じ文字列を許します。数量・容量は1〜1,000,000の整数μL、残量は0も許容します。入力は公開型に従うものとし、数量範囲・参照・業務制約への違反を検査対象にします。エラーコード表も公開し、複数違反時は該当するコードのいずれも正解とすれば、不要な検証順序の指定を避けられます。

| 規則群 | requestに明記する規則 |
|---|---|
| **R1 参照・収容** | 場所・容器・責任者は初期カタログに登録済み。残量のある試料は必ず一つの容器に入り、一つの容器には最大一試料。残量は容器容量以下。試料ID・予約IDは終了後も再利用不可。 |
| **R2 系譜・数量保存** | `receive`だけが根試料を作る。`split`は新規の子を1個以上まとめて作り、合計量を親から引く。親関係は不変、子の根IDは親と同じ。分取総量は親の利用可能量以下。根の受入量＝系譜全体の現在残量＋累積消費量＋累積廃棄量。分取は消費に数えない。 |
| **R3 予約・消費** | 利用可能量＝残量−有効予約量。予約は残量を減らさず利用可能量だけ減らす。取消は予約を解除する。消費は有効予約の全量だけ行い、残量と予約量を同時に減らす。部分消費・予約なし消費は対象外。取消済み・消費済み予約への新規操作は拒否。 |
| **R4 状態・廃棄** | 試料状態は`ACTIVE / DEPLETED / DISCARDED`。分取・消費で残量0になると`DEPLETED`。廃棄は予約のない`ACTIVE`試料の残量全量に対して行い、`DISCARDED`になる。終端状態から復活不可。終端時に容器を空ける。親の終端化は子に波及しない。 |
| **R5 容器・場所** | 試料の場所は現在の容器から導出する。移動先は操作開始時点で空いており容量が足りる別容器。分取先も開始時点で空いた互いに異なる容器。移動は試料量・予約・系譜・責任者を変えない。有効予約があっても移動できる。 |
| **R6 保管責任** | 受入時に責任者を指定し、分取時に子が親の現在の責任者を引き継ぐ。責任者変更は指定試料だけに作用し、祖先・子孫には波及しない。予約中でも変更可能。移動・責任者変更は`ACTIVE`試料だけに許可。 |
| **R7 重複処理** | 成功済みeventIdに同じ操作・引数を再送した場合、元のReceiptを返し状態・履歴を変えない。内容が違えばID競合。比較はオブジェクトのキー順を無視し、配列順は区別する。成功済み再送の判定は現在状態の業務検証より先に行う。失敗したeventIdは未登録で、再試行できる。 |
| **R8 原子性・履歴** | 成功した新規コマンドごとにイベントを一つ追加し、連番を一つ進める。失敗時は数量・状態・予約・容器割当・系譜・履歴・eventId登録のすべてを変えない。複数子の分取も全体成功か全体失敗。履歴は操作と引数を保持し、後の操作で書き換えない。 |

事前指定する混同対は次の8組が適切です。

| 混同対 | 意味の区別 |
|---|---|
| 試料ID／容器ID | 中身の識別／入れ物の識別 |
| 親試料／根試料 | 直前の分取元／受入起点 |
| 残量／利用可能量 | 物理的に残る量／未予約の量 |
| 予約／消費 | 使用権の確保／物理量の減少 |
| 分取／消費 | 系譜内の量の移動／系譜外への量の流出 |
| 場所／保管責任者 | 物理的所在／管理主体 |
| 枯渇／廃棄 | 分取・消費による残量0／廃棄操作による終了 |
| eventId／reservationId | 操作の再送識別／予約の識別 |

基本問題は各操作を単独で成立させるもの、組合せ問題は例えば次のようにします。

- 100μL受入→40予約→50分取：親残量50、予約40、利用可能量10。
- 親の全量分取→親が枯渇しても子は操作可能。
- 予約→別場所の容器へ移動→責任者変更→予約を消費。
- 子を二つ分取し、二つ目だけ容量超過：一つ目を含め全変更なし。
- 消費成功後に同じeventIdを再送：二重消費せず、元のReceiptを返す。

これらの**政策と期待値を使う公開例は三条件共通**にします。隠すのは別の値・ID・操作列です。採点は規則群を等重みにし、各群の基本と組合せを分けて報告します。存在しない対応をPRDが省略した場合は、用語一致の成功にも混同にもせず、別途「未記載」と数えます。

なお、合意済み事項への補足として、**`chmod 000`だけでは、ファイル所有者で動くエージェントによる権限変更を防げません。** 正答・隠し採点・結果は、実行主体から読めず権限変更もできない別ユーザーまたは隔離環境に置くことを隔離の条件にしてください。

# 요청 — 연구실 시료 보관 엔진

가상의 연구실에서 시료(액체)를 받아들이고, 나눠 담고, 예약하고, 쓰고, 버리고, 옮기는 일을 기록하는 엔진을 만들어 주세요.
실제 연구실 관행은 신경 쓰지 말고, **아래에 적힌 규칙만** 따르면 됩니다.

- 코드는 `src/lab/lab.ts`에 만들고 `createLab(catalog: Catalog): Lab`을 내보내 주세요.
- 함수 모양·결과 모양·오류 코드는 이미 있는 `src/lab/types.ts`를 그대로 따르세요(고치지 마세요).
- 메모리 안에서 한 번에 한 호출씩 처리합니다. 저장소·동시 실행·실제 시각은 다루지 않습니다.
- 실패는 예외를 던지지 말고 `{ ok: false, code }`로 돌려줍니다.

## 대상
- **장소(location)·용기(container)·보관 책임자(custodian)** 는 `createLab`에 넘긴 목록에 있는 것만 존재합니다. 용기는 장소 하나에 고정돼 있고 용량(capacity)이 있습니다.
- **시료(sample)** 는 용기에 담긴 액체입니다. 양은 정수 μL입니다.
- **예약(reservation)** 은 시료의 일정량을 쓰겠다고 잡아 두는 것입니다.
- **이벤트(event)** 는 성공한 명령 하나의 기록입니다. 모든 명령은 첫 인자로 `eventId`를 받습니다.

## 규칙
### R1 참조·수용
1. 장소·용기·책임자는 처음 목록에 있는 것만 쓸 수 있습니다. 없는 용기는 `UNKNOWN_CONTAINER`, 없는 책임자는 `UNKNOWN_CUSTODIAN`, 없는 시료는 `UNKNOWN_SAMPLE`, 없는 예약은 `UNKNOWN_RESERVATION`.
2. ACTIVE 시료는 반드시 용기 하나에 담겨 있고, 용기 하나에는 시료가 최대 하나입니다. 차 있는 용기에 넣으려 하면 `CONTAINER_OCCUPIED`.
3. 시료의 남은 양(remaining)은 담긴 용기의 용량 이하입니다. 넘으면 `CAPACITY_EXCEEDED`.
4. 시료 ID·예약 ID는 한 번 쓰면(그 시료·예약이 끝난 뒤에도) 다시 쓸 수 없습니다 → `ID_TAKEN`. ID는 종류마다 따로 고유합니다 — 시료 ID와 용기 ID가 같은 글자여도 됩니다.
5. 양(qty)은 1 이상 1,000,000 이하의 정수입니다. 아니면 `INVALID_INPUT`. 분취할 자식 목록이 비어 있어도 `INVALID_INPUT`.

### R2 계보·수량 보존
1. `receive`만 계보의 시작(root) 시료를 만듭니다. 받아들인 시료는 parentId가 null, rootId가 자기 자신입니다.
2. `split`은 부모 시료에서 새 자식 시료를 한 번에 1개 이상 만들고, 자식 양의 합을 부모의 남은 양에서 뺍니다. 자식의 parentId는 부모, rootId는 부모의 rootId입니다. 부모·계보 관계는 나중에 바뀌지 않습니다.
3. 나눠 담을 수 있는 총량은 부모의 **이용 가능량** 이하입니다(R3). 넘으면 `INSUFFICIENT`.
4. 분취는 소비가 아닙니다. 계보 전체에서 늘 이렇게 맞아야 합니다: 시작 시료가 받은 양 = 계보 안 모든 시료의 남은 양 합 + 누적 소비량 합 + 누적 폐기량 합.

### R3 예약·소비
1. **이용 가능량 = 남은 양 − ACTIVE 예약 양의 합(reserved).**
2. 예약은 남은 양을 줄이지 않고 이용 가능량만 줄입니다. 이용 가능량보다 많이 예약하면 `INSUFFICIENT`. ACTIVE가 아닌 시료는 예약할 수 없습니다(`NOT_ACTIVE`).
3. `cancel`은 ACTIVE 예약을 CANCELED로 바꾸고 잡아 둔 양을 풀어 줍니다.
4. `consume`은 ACTIVE 예약의 **양 전체**를 씁니다: 남은 양과 reserved를 함께 그만큼 줄이고, 시료의 consumedQty를 늘리고, 예약을 CONSUMED로 바꿉니다. 일부만 쓰거나 예약 없이 쓰는 기능은 없습니다.
5. CANCELED·CONSUMED 예약에 다시 `cancel`·`consume`하면 `RESERVATION_CLOSED`.

### R4 상태·폐기
1. 시료 상태는 `ACTIVE`·`DEPLETED`·`DISCARDED`입니다.
2. 분취나 소비로 남은 양이 0이 되면 `DEPLETED`(바닥남)입니다.
3. `discard`(폐기)는 ACTIVE 예약이 없는 ACTIVE 시료의 남은 양 전부를 버립니다: discardedQty에 더하고 남은 양 0, 상태 `DISCARDED`. ACTIVE 예약이 있으면 `HAS_RESERVATION`.
4. DEPLETED·DISCARDED는 끝난 상태입니다. 되살릴 수 없고, 분취·예약·폐기·이동·책임자 변경은 모두 `NOT_ACTIVE`.
5. 끝난 시료는 용기를 비웁니다(containerId null). 그 용기는 다른 시료가 쓸 수 있습니다.
6. 부모가 끝나도 자식에게는 영향이 없습니다.

### R5 용기·장소
1. 시료의 장소는 지금 담긴 용기의 장소입니다(따로 저장하지 않음).
2. `move`는 시료를 다른 용기로 옮깁니다. 옮길 용기는 명령 시작 시점에 비어 있고 용량이 남은 양 이상이어야 합니다. 지금 담긴 용기로 옮기려 하면 `CONTAINER_OCCUPIED`.
3. 분취할 자식의 용기도 명령 시작 시점에 비어 있어야 하고, 자식끼리 같은 용기를 쓸 수 없습니다(`CONTAINER_OCCUPIED`). 부모가 담긴 용기도 차 있는 용기입니다.
4. 이동은 양·예약·계보·책임자를 바꾸지 않습니다. ACTIVE 예약이 있어도 옮길 수 있습니다.

### R6 보관 책임
1. `receive`할 때 책임자를 정합니다. 분취한 자식은 그 순간 부모의 책임자를 이어받습니다.
2. `transferCustody`는 지정한 시료 하나의 책임자만 바꿉니다. 부모·자식에게 번지지 않습니다. 예약 중이어도 바꿀 수 있습니다.
3. 이동·책임자 변경은 ACTIVE 시료만 됩니다.

### R7 같은 명령 다시 보내기
1. 이미 **성공한** eventId로 같은 명령·같은 인자를 다시 보내면, 처음 받은 Receipt를 그대로 돌려주고 상태·이력은 바꾸지 않습니다. 지금 상태로는 실패할 명령이어도 마찬가지입니다(이 판단을 다른 검사보다 먼저 합니다).
2. 같은 eventId로 다른 명령이나 다른 인자를 보내면 `EVENT_CONFLICT`.
3. 인자 비교에서 객체의 키 순서는 무시하고, 배열 순서는 구별합니다.
4. 실패한 명령의 eventId는 기록되지 않습니다 — 같은 eventId로 다시 시도할 수 있습니다.

### R8 원자성·이력
1. 성공한 새 명령마다 이벤트 하나를 남기고 seq를 1 늘립니다(첫 seq는 1).
2. 실패하면 양·상태·예약·용기 배정·계보·이력·eventId 기록 무엇도 바뀌지 않습니다. 여러 자식을 나누는 분취도 모두 성공하거나 모두 실패합니다.
3. 이력은 명령 이름(op)과 인자(args, eventId 제외)를 그대로 담고, 나중 명령이 바꾸지 않습니다. args 모양은 `types.ts`의 `EventView.args` 설명대로입니다(R7의 "같은 인자"도 이 args로 비교).

규칙을 여러 개 어기는 호출은 어긴 규칙의 오류 코드 중 무엇을 돌려줘도 됩니다.

## 공개 예시 (용기 C1~C9는 모두 용량 1,000, 책임자 U1·U2)
1. S1 100 받음 → S1에 40 예약 → S1에서 S2로 50 분취: S1 남은 양 50·reserved 40(이용 가능량 10), S2 50.
2. S1 100 받음 → S2 60, S3 40으로 분취: S1은 DEPLETED·용기 비움, S2·S3은 계속 쓸 수 있음.
3. S1 받음 → 예약 R1 → 다른 장소 용기로 move → U2로 transferCustody → R1 consume: 모두 성공, 책임자 U2.
4. S1 100 받음 → 자식 두 개(30은 빈 용기, 둘째 20은 차 있는 용기)로 분취: 실패, 아무것도 바뀌지 않음(첫째 자식도 없음).
5. consume 성공 뒤 같은 eventId·같은 인자로 다시 consume: 처음 Receipt를 그대로, 두 번 쓰지 않음.
